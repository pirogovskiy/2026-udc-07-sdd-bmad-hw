# Специфікація: рушій знижок (рівень лояльності + промокоди)

**Статус:** agreed
**Джерело:** `materials/feature-request.md`
**Автор рішень:** Sviatoslav Pirogovskiy

---

## 1. Мета

Дозволити застосувати до замовлення знижку за рівнем лояльності та один чи
кілька промокодів (відсоткових або фіксованих) так, щоб результат був
**детермінованим**: два різні прогони реалізації цієї специфікації на
однакових вхідних даних завжди рахують однакову суму до копійки. Зараз
`tierPercent` існує, але ніде не застосовується — після релізу знижка за
рівнем і промокоди реально зменшують суму до сплати.

## 2. Поза скоупом

- Ліміти на використання промокоду (кількість разів, «один на клієнта») —
  немає стану клієнта, який це б відстежував.
- Валідація самих об'єктів `Coupon` (наприклад, `value` поза межами 0–100 для
  відсоткового типу) — вважаємо каталог промокодів довіреними вхідними даними.
- Знижки на доставку — доставка рахується як і раніше, `shippingKopecks` не
  змінюється і знижок не отримує.
- UI/повідомлення користувачу про причину відмови промокоду — рушій лише
  повертає, які коди застосувались; текст помилки — відповідальність
  checkout-шару, не цієї функції.
- Валюти, відмінні від гривні/копійки.
- Логування, аналітика, аудит використання промокодів.

## 3. Рішення щодо неоднозначностей

| # | Питання | Рішення | Чому саме так |
|---|---|---|---|
| D-1 | Промокод і рівень складаються чи застосовуються послідовно? | Послідовно: спершу знижка за рівнем від сирого підсумку товарів, потім кожен застосовний промокод — у порядку, в якому клієнт їх ввів (`order.coupons`), кожен від залишку, що лишився після попереднього кроку. | Складання відсотків (10%+15%=25%) при кількох знижках легко перевищує 100% і стає непрозорим. Послідовне застосування завжди дає результат ≤ підсумку і легко перевіряється покроково. |
| D-2 | База знижки — товари чи товари + доставка? | Лише сума товарів (`subtotalKopecks`). Доставка рахується окремо і ніколи не дисконтується. | Ticket каже «знижки», доставка — окрема, вже повністю специфікована лінія (`shippingKopecks`) поза скоупом цієї фічі. |
| D-3 | Кілька промокодів — усі / найвигідніший / перший? | Усі валідні застосовуються (послідовно, п. D-1), **окрім** випадку, коли два чи більше застосовних промокоди націлені на **одну й ту саму категорію** — тоді з них береться лише **один**, той що дає найбільшу знижку для цієї категорії; решта мовчки ігноруються (не потрапляють у `appliedCoupons`). Промокоди без `category` не конфліктують між собою і не конфліктують із категорійними. | Дає клієнту відчути вигоду від кількох кодів (вимога з тікета, п.3, «клієнт має відчувати вигоду від обох»), але не дозволяє необмежено складати знижки на той самий товар. |
| D-4 | Округлення: де і в який бік? | Кожна окрема сума знижки (знижка за рівнем; кожен промокод) округлюється до цілої копійки **окремо, в момент обчислення цієї суми**, до того як її віднімають від залишку. Округлення — до найближчої копійки; рівно пів копійки округлюється **вгору**. Кінцевий підсумок ніде додатково не округлюється (він уже сума цілих копійок). | Округлення на кожному кроці, а не в кінці, унеможливлює «плавання» — кожна проміжна сума завжди ціла копійка, і два прогони з однаковим порядком кроків завжди збігаються. Округлення вгору для .5 — проста, детермінована, всім відома монетка. |
| D-5 | Промокод на категорію рахується від чого? | Від суми **лише тих рядків замовлення, чия `category` збігається** з `coupon.category` — сирої, до застосування будь-яких знижок (див. D-13). Якщо в замовленні немає жодного рядка цієї категорії, база = 0 і знижка = 0 (промокод не помилка, просто не діє). | Промокод «на категорію fresh» логічно не повинен зменшувати вартість digital-товарів у тому ж замовленні. |
| D-6 | `minSubtotalKopecks` перевіряється до чи після інших знижок? | До: перевіряється проти **сирого** `subtotalKopecks` замовлення (до знижки за рівнем і до будь-яких інших промокодів). | Мінімальна сума — це умова на розмір замовлення клієнта, а не на те, скільки знижок йому вже дали. Перевірка після знижок означала б, що застосування одного промокоду може «вимкнути» право на інший — заплутана й недокументована побічна дія. |
| D-7 | Чи може підсумок стати відʼємним? Чи є нижня межа? | Ні. Сума знижок (рівень + усі застосовні промокоди) обмежується так, щоб сума товарів після знижок не була меншою 0 — фіксовані промокоди «зрізаються» до залишку, що є на момент їх застосування. Доставка (якщо є) додається завжди, поверх — підсумок замовлення теж ніколи не може бути відʼємним. | Відʼємна ціна товару не має бізнес-сенсу; клієнту не платять за покупку. |
| D-8 | Прострочений промокод — тиха відмова чи явна помилка? | Тиха відмова: код просто не потрапляє в `appliedCoupons`, решта промокодів і знижка за рівнем рахуються як завжди. Функція не кидає виняток. | Checkout не повинен ламатись через один застарілий код серед кількох введених; рушій лише повідомляє, що фактично застосувалось (`appliedCoupons`), а рішення показати попередження — за UI-шаром (поза скоупом, п.2). |
| D-9 | Промокод, якого немає в каталозі (`coupons: Coupon[]`), або з кодом, що не збігається жодним чином (регістр враховується)? | Так само як D-8 — тиха відмова, ігнорується. Порівняння кодів — **точне, чутливе до регістру** (`===`), без нормалізації регістру чи пробілів. | Одна поведінка на «код не спрацював» простіша для реалізації й тестування, ніж окрема гілка на «код невідомий» проти «код простроченний». Чутливість до регістру — консистентно з тим, що коди — просто рядки в контракті, без окремого правила нормалізації. |
| D-10 | Клієнт ввів однаковий код двічі (`order.coupons = ["SAVE10", "SAVE10"]`)? | Дублікати одного коду згортаються — застосовується один раз. | Інакше клієнт міг би подвоїти знижку, просто ввівши той самий код повторно; тікет про це не просить. |
| D-11 | Фіксований промокод (`kind: "fixed"`) більший за базу, до якої застосовується? | Знижка «зрізається» до розміру бази (загальної суми товарів або суми категорії — залежно від D-5), а не йде в мінус і не переноситься на інші рядки/промокоди. | Наслідок D-7 — сума ніколи не йде в мінус, і сума знижки як «зайва» частина нікуди логічно не переноситься без окремої вимоги в тікеті. |
| D-12 | Порожнє замовлення (`items: []`)? | `subtotalKopecks` = 0, знижка за рівнем = 0, будь-який промокод з `minSubtotalKopecks > 0` не проходить (0 не досягає мінімуму), сума знижок = 0. Не помилка. | Порожнє замовлення — валідний граничний випадок для `subtotalKopecks` (вже перевірено в наявних тестах `pricing.test.ts`), рушій знижок має поводитись з ним так само беззаперечно. |
| D-13 | Бази для перевірок (сума категорії з D-5, мінімальна сума з D-6) рахуються від «сирих» значень чи від значень, що вже врахували попередні знижки? | Завжди від **сирих** значень замовлення (сума товарів або сума категорії до жодних знижок). Сама ж сума знижки, щойно обчислена від такої бази, віднімається **послідовно** від поточного залишку (п. D-1). | Розділяє «чи застосовується правило» (залежить лише від замовлення клієнта) від «скільки саме зняти» (залежить від порядку застосування). Без цього правила D-1 (послідовність) і D-5/D-6 (бази) суперечили б одне одному в неочевидний спосіб. |

## 4. Критерії приймання

- **AC-1:** КОЛИ замовлення на 1 000 грн (100 000 коп.) від Gold-клієнта без промокодів, ТОДІ знижка за рівнем = 10 000 коп., сума товарів після знижок = 90 000 коп.
- **AC-2:** КОЛИ замовлення на 1 000 грн від Silver-клієнта (5%) з одним відсотковим промокодом 15% без обмежень, ТОДІ знижка за рівнем = 5 000 коп. (залишок 95 000), знижка за промокодом = round(95 000 × 0.15) = 14 250 коп. (залишок 80 750 коп.).
- **AC-3:** КОЛИ введено два промокоди на одну категорію (20% і 30% на `fresh`, база категорії = 40 000 коп.), ТОДІ застосовується лише вигідніший (30%, знижка 12 000 коп.), другий у `appliedCoupons` не потрапляє.
- **AC-4:** КОЛИ промокод простроченний (`expiresAt` у минулому), ТОДІ він мовчки ігнорується (не в `appliedCoupons`, винятку немає), решта знижок рахуються як завжди.
- **AC-5 (граничний):** КОЛИ фіксований промокод 150 грн (15 000 коп.) застосовано до замовлення на 100 грн (10 000 коп.) без рівневої знижки, ТОДІ знижка за промокодом зрізається до 10 000 коп., сума товарів після знижок = 0, підсумок = вартість доставки (не менше 0, ніде в мінус).
- **AC-6:** КОЛИ `minSubtotalKopecks` промокоду = 95 000 коп., сирий підсумок замовлення = 100 000 коп., а Gold-знижка (10%) зменшила б залишок до 90 000 коп., ТОДІ промокод усе одно застосовується (перевірка йде проти сирих 100 000, а не проти залишку 90 000).
- **AC-7:** КОЛИ промокод на категорію `fresh` (10%) застосовано до замовлення з товарами `fresh` на 30 000 коп. і `standard` на 70 000 коп., ТОДІ знижка = round(30 000 × 0.10) = 3 000 коп. (не 10% від усього замовлення).
- **AC-8 (граничний, округлення):** КОЛИ обчислена знижка дає рівно пів копійки (напр. 50% від бази 15 коп. = 7.5 коп.), ТОДІ знижка округлюється вгору до 8 коп.
- **AC-9 (граничний, порожнє замовлення):** КОЛИ замовлення без товарів (`items: []`), ТОДІ підсумок товарів = 0, знижка за рівнем = 0, будь-який промокод з `minSubtotalKopecks > 0` не застосовується, доставка = 0 (порожній список товарів вважається «увесь цифровий»), загальний підсумок = 0.
- **AC-10:** КОЛИ клієнт вводить код, якого немає в переданому каталозі промокодів **точно** (включно з кодом, що відрізняється лише регістром — напр. каталог містить `SAVE10`, а клієнт ввів `save10`), ТОДІ код мовчки ігнорується так само, як прострочений (D-9), без винятку; зіставлення кодів — точне і чутливе до регістру, без нормалізації.
- **AC-11:** КОЛИ клієнт вводить один і той самий код промокоду двічі (`["SAVE10", "SAVE10"]`), ТОДІ знижка застосовується лише один раз.

## 5. Контракт

```ts
import type { Order, Coupon } from "./types.js";

export interface PriceBreakdown {
  /** Сира сума товарів, до жодних знижок. */
  subtotalKopecks: number;
  /** Знижка за рівнем лояльності, у копійках (0, якщо тариф "none"). */
  tierDiscountKopecks: number;
  /** Сумарна знижка від усіх застосованих промокодів, у копійках. */
  couponDiscountKopecks: number;
  /** Коди промокодів, що фактично застосувались (після D-3/D-8/D-9/D-10), у порядку застосування. */
  appliedCoupons: string[];
  /** subtotalKopecks - tierDiscountKopecks - couponDiscountKopecks, не менше 0. */
  goodsTotalKopecks: number;
  /** Як і раніше, з pricing.ts — доставка знижок не отримує. */
  shippingKopecks: number;
  /** goodsTotalKopecks + shippingKopecks. */
  totalKopecks: number;
}

/**
 * @param order замовлення; order.coupons — коди, введені клієнтом, у порядку введення.
 * @param catalog повний каталог промокодів, серед яких шукаються введені коди.
 */
export function priceOrder(order: Order, catalog: Coupon[]): PriceBreakdown;
```
